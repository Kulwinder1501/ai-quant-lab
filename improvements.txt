# 4. Required Architectural Improvements

## 4.1 Separate online and offline workflows

Create two clearly separated execution paths.

### Online decision workflow

Runs during a paper-trading or historical-replay session.

```text
Market event
    ↓
Point-in-time feature calculation
    ↓
Champion model inference
    ↓
Strategy orchestration
    ↓
Risk evaluation
    ↓
Paper-trading execution
    ↓
Audit record
    ↓
SSE dashboard update
```

The online workflow must never:

* Train a model
* Promote a model
* Modify model parameters
* Change feature definitions
* Learn directly from a single trade
* Write uncontrolled trading rules
* Use future market data

### Offline model lifecycle

Runs after market hours or on a controlled schedule.

```text
Data validation
    ↓
Label completion
    ↓
Versioned feature-dataset generation
    ↓
Candidate training
    ↓
Walk-forward evaluation
    ↓
Cost-aware backtesting
    ↓
Candidate registration
    ↓
Shadow paper trading
    ↓
Promotion-gate evaluation
    ↓
Manual or controlled promotion
```

Daily training is allowed.

Daily automatic champion replacement is not allowed.

## 4.2 Refactor the autonomous agent

The current autonomous-agent or strategy-engine module has too many responsibilities.

Refactor it into a deterministic:

```text
strategy-orchestrator
```

or:

```text
decision-engine
```

The strategy orchestrator should:

* Accept normalized feature data
* Call model inference
* Receive model predictions
* Apply strategy-specific rules
* Produce a proposed trade decision
* Send the proposal to the risk engine
* Record decision reasons
* Remain independent from HTTP and TypeORM

The orchestrator must not:

* Calculate account balances
* Directly execute trades
* Promote models
* Train models
* Change its own rules after one trade
* Own news ingestion
* Own database persistence

Use contracts similar to:

```typescript
type TradeDirection = "LONG" | "SHORT" | "NO_TRADE";

interface TradeDecision {
  instrumentId: string;
  decisionTimestamp: Date;

  modelTaskId: string;
  modelVersionId: string;

  direction: TradeDirection;
  predictedProbability: number;
  confidence: number;

  marketRegime: string;
  regimeConfidence: number;

  proposedEntryPrice: number | null;
  proposedStopLoss: number | null;
  proposedTargetPrice: number | null;

  reasonCodes: string[];
}
```

# 12. Data Leakage Prevention

Every feature and prediction must respect point-in-time availability.

Enforce:

```text
featureAvailabilityTimestamp <= predictionTimestamp
labelCompletionTimestamp > predictionTimestamp
```

Reject pipelines that:

* Use future candles
* Use a completed day’s high before market close
* Use future news
* Fit scalers on the complete dataset
* Fill missing data with future values
* Randomly shuffle time-series rows
* Use revised values unavailable at prediction time
* Reuse the final holdout set for repeated model selection
* Calculate indicators across validation boundaries incorrectly

Add automated leakage tests.

At least one test must intentionally introduce future data and verify that the pipeline rejects it.

# 17. Promotion Gates

A candidate may become champion only after passing all mandatory gates.

Required gates:

1. Dataset validation passed
2. Feature schema validated
3. Leakage tests passed
4. Training is reproducible
5. Candidate beats naive baselines
6. Walk-forward evaluation passed
7. Net performance remains positive after costs
8. Increased-slippage stress test passed
9. Maximum drawdown remains within limits
10. Minimum trade count is satisfied
11. Performance is not concentrated in one period
12. Required regime tests passed
13. Probability calibration is acceptable
14. Tail risk remains acceptable
15. Shadow paper-trading period completed
16. Candidate materially improves or complements the champion
17. Model artifact is valid and loadable
18. Input and output schemas are compatible
19. Rollback is available
20. Promotion decision is audited

Initially require manual approval.

Do not automatically promote a candidate only because it has the highest backtest profit.

# 24. Coding Standards

Use:

* TypeScript strict mode
* Explicit domain contracts
* Zod validation at application boundaries
* Dependency inversion
* Repository interfaces
* Use-case or application-service classes
* Small focused files
* Clear naming
* Database transactions
* Structured logging
* Idempotent job execution
* Reproducible ML runs
* Deterministic random seeds
* Unit tests
* Integration tests
* Migration tests

Avoid:

* `any`
* Hidden database access in domain code
* Circular module dependencies
* Fat controllers
* Large service classes
* Financial logic inside route handlers
* Silent exception swallowing
* Hard-coded model versions
* Hard-coded thresholds without configuration
* Duplicate cron execution
* Direct LLM-to-trade execution
* Direct model-to-order execution
* Self-modifying production rules

# 26. Mandatory Safety Rules

The platform must remain paper-trading only.

Do not:

* Add live broker order placement
* Add broker-write credentials
* Add automatic real-money execution
* Add a hidden live-trading mode
* Allow an LLM to place trades
* Allow candidate models to bypass risk checks
* Automatically promote models without validation
* Modify production strategies after one trade
* Claim guaranteed profitability
* Treat a backtest as proof of future results
* Mix simulated and real datasets without clear source labels
* Delete previous champion artifacts
* Use future data in features
* Randomly split financial time-series data
